# Plano de Implementação — As Águas de Apsu: Sprint 5

## Contexto e Diagnóstico

O jogo é um side-scroller 2.5D em JavaFX com 3 fases (P1, P2, P3). Os modelos 3D reais já existem como `.blend` em `personagens/blends/` e os sprites já foram renderizados em `src/main/resources/sprites/`. O código principal está distribuído entre `GameContext.java` (lógica), `RenderEngine.java` (renderização), `HeroEntity.java`, `EnemyType.java`, `SceneryElement.java`.

### Bugs Identificados

| # | Problema | Causa Raiz |
|---|---|---|
| B1 | **Deformação do personagem no menu** | `drawHero()` e `drawMenu()` usam aspect ratio dinâmico baseado no frame da animação atual. Frames diferentes (attack1 vs swim) têm dimensões diferentes → largura oscila com a troca de frame. |
| B2 | **Enguia desproporcional na Fase 1** | `EnemyType.ENGUIA` tem `width=200, height=27` — esses valores produzem uma enguia ultra-wide e achatada, desproporcional aos outros inimigos (Peixe: 100×142). |
| B3 | **Bolhas não funcionam na Fase 2** | `tryShoot()` checa `hero.hasBubblePower()`, que começa `false`. O baú está posicionado em `chestWX=1600` mas a colisão no chest usa `camera.toScreenX(chestWX)` — as coordenadas do projétil são criadas com posição de tela, não de mundo; mas `updateProjectiles()` faz o movimento e colisão com inimigos usando coordenadas de tela (`camera.toScreenX(e.getWorldX())`). O problema real é que a bolha é criada em coordenadas de tela mas não é convertida para coordenadas de mundo antes de ser adicionada. Além disso, a verificação `hasBubblePower()` em `tryShoot()` funciona, mas ao abrir o baú o poder é setado. Confirmando: **o bug é que a bolha é gerada em coordenadas de tela** (`hero.getBubbleSpawnX()` retorna `hero.getX()` que é coordenada de MUNDO em P1/P2, mas em P2 `screenHeroX = camera.toScreenX(hero.getX())` — o herói está no mundo mas `getBubbleSpawnX()` usa a posição de mundo diretamente). Verificando `updateProjectiles()`: colisão com inimigos usa `camera.toScreenX(e.getWorldX())` vs `p.getX()`/`p.getY()`. **A bolha é criada em posição de mundo, mas se move e colide em posição de tela.** Em P3 não há câmera scroll (herói é limitado a 1366px), então funciona. Em P2 a câmera rola e as coordenadas se tornam inconsistentes. |

## User Review Required

> [!IMPORTANT]
> O sistema de coordenadas é o maior desafio técnico. **Projéteis, inimigos e herói usam coordenadas de mundo**, mas a câmera converte para tela na hora de renderizar. Isso exige que a colisão de projéteis com inimigos também use coordenadas de mundo (não de tela). A refatoração de coordenadas afeta `updateProjectiles()`, `checkEnemyCollisions()`, `tryShoot()` e o `RenderEngine`. O fix garante consistência em todas as 5 fases.

> [!WARNING]
> A geração de novos `.blend` para Fases 4 e 5 requer o Blender instalado. Os scripts Python de geração procedural existentes (em `personagens/scripts/`) usam caminhos Windows. Vou adaptar para Linux e executar se o Blender estiver disponível, gerando novos assets 3D para os novos inimigos e cenários. Se não disponível, os sprites serão renderizados proceduralmente no Java como fallback geométrico de alta qualidade.

## Verificação de Bugs

### Bug B1 — Deformação no Menu
A correção: no `drawMenu()`, calcular `pw` uma única vez com base na imagem ESTÁTICA do herói (não do frame animado):
```java
// ANTES (problemático): aspect ratio muda com cada frame
double aspect = frame.getWidth() / frame.getHeight();
double pw = ph * aspect;

// DEPOIS (correto): aspect ratio calculado da imagem estática
double aspect = (imgSwim != null && imgSwim.getHeight() > 0)
    ? imgSwim.getWidth() / imgSwim.getHeight() : 0.5;
double pw = ph * aspect; // Calculado 1x, não por frame
```

### Bug B2 — Enguia Desproporcional
```java
// ANTES
ENGUIA(1, 200, 27, ...)
// DEPOIS — proporção widescreen horizontal natural para enguia
ENGUIA(1, 160, 85, ...)
```

### Bug B3 — Bolhas na Fase 2
O problema central: projéteis criados com `hero.getX()` (mundo) mas colisão com `camera.toScreenX(e.getWorldX())` (tela).

**Solução**: Mudar `updateProjectiles()` para usar coordenadas de mundo consistentemente:
```java
// Colisão bolha vs inimigo — MUNDO consistente
double ex = e.getWorldX(); // sem conversão de câmera
if (rectsHit(p.getX(), p.getY(), 16, 16, ex, ...))
```
E a render: `p.getX()` → `camera.toScreenX(p.getX())` no `drawProjectiles()`.
